# 第 2 课：生命周期与初始化

> 覆盖源码第 113-195 行。这一课讲清楚插件的三个生命周期函数：`plugin_precache`、`plugin_init`、`plugin_end`，以及初始化时注册的所有命令、菜单、事件。

---

## 2.1 plugin_precache：预缓存阶段（第 115-121 行）

```pawn
public plugin_precache() {
    server_print("[SkinSystem] plugin_precache: 开始加载模型...");
    load_player_models();
    precache_all_models();
    server_print("[SkinSystem] plugin_precache: 完成! T=%d, CT=%d, Knife=%d",
        ArraySize(g_aTModels), ArraySize(g_aCTModels), ArraySize(g_aKnifeModels));
}
```

`plugin_precache` 是 AMXX 在**服务器启动、加载地图时**调用的第一个函数。它只调用一次。

这里做了两件事：
1. `load_player_models()` —— 读取配置文件，把皮肤列表装进内存（第 3 课详讲）
2. `precache_all_models()` —— 把每个模型文件预缓存（第 4 课详讲）

`server_print` 在服务器控制台打印日志。`ArraySize()` 返回数组里有多少个元素，用来确认加载了多少皮肤。

> 为什么必须在这里加载模型？因为 CS 引擎要求模型**必须在预缓存阶段**注册，否则游戏里会显示成错误模型或直接崩溃。这是引擎的硬性规定。

## 2.2 plugin_init：初始化阶段（第 126-195 行）

`plugin_init` 是插件初始化的核心，注册了插件信息、CVAR、消息钩子、命令、菜单、事件。我们一段一段看。

### 2.2.1 注册插件信息（第 127 行）

```pawn
register_plugin(PLUGIN_NAME, PLUGIN_VERSION, PLUGIN_AUTHOR);
```

把第 1 课定义的三个宏传给 AMXX。之后在服务器控制台输入 `amxx plugins` 就能看到这个插件的名字、版本、作者。

### 2.2.2 注册 CVAR（第 130 行）

```pawn
register_cvar("skinsys_advanced", "1");
```

`register_cvar` 注册一个服务器变量（CVAR）。这里注册了 `skinsys_advanced`，默认值 `1`。

> 注释里说"防止 player_models.inc 冲突"。这是一个标记变量，告诉其他插件"高级皮肤系统已激活"。这个 CVAR 在本版本里只是打个标记，没有实际读取逻辑。

### 2.2.3 注册武器切换消息（第 133-134 行）

```pawn
register_message(get_user_msgid("CurWeapon"), "FM_CurWeapon");
```

`CurWeapon` 是 CS 引擎发给客户端的一条**消息**，每当玩家切换武器时触发。这里注册了一个钩子 `FM_CurWeapon`，让插件在玩家切刀时重新应用刀皮肤。

> 注释特别强调："CurWeapon 是消息(message)，必须用 register_message，不能用 register_event"。这是 AMXX 的一个常见坑：`register_event` 只能接事件（event），`CurWeapon` 是消息（message），必须用 `register_message`。

### 2.2.4 打开 nvault 数据库（第 137 行）

```pawn
g_iVault = nvault_open("skinsys_skin_vault");
```

`nvault_open` 打开（或创建）一个名为 `skinsys_skin_vault` 的数据库，返回句柄存到 `g_iVault`。之后所有存档读写都用这个句柄。

### 2.2.5 注册玩家命令（第 140-162 行）

```pawn
register_clcmd("say /skin", "cmdSkinMain");
register_clcmd("say /models", "cmdSkinMain");
register_clcmd("say /skins", "cmdSkinMain");
```

`register_clcmd` 注册**客户端命令**。玩家在聊天框输入 `say /skin` 时，会触发 `cmdSkinMain` 函数。

这里注册了一堆命令，全部指向 `cmdSkinMain`（打开主菜单）：

| 命令 | 触发函数 | 说明 |
|------|---------|------|
| `say /skin` | `cmdSkinMain` | 主菜单 |
| `say /models` | `cmdSkinMain` | 别名 |
| `say /skins` | `cmdSkinMain` | 别名 |
| `say /model` | `cmdSkinMain` | 兼容旧命令 |
| `say_team /skin` 等 | `cmdSkinMain` | 队伍聊天也能用 |

> `say_team` 是队伍聊天。注册 `say_team /skin` 意味着在队伍频道输入 `/skin` 也能打开菜单。这是为了兼容不同玩家的输入习惯。

### 2.2.6 注册直接选择子菜单（第 146-148 行）

```pawn
register_clcmd("say /skin_t", "cmdSkinSelectT");
register_clcmd("say /skin_ct", "cmdSkinSelectCT");
register_clcmd("say /skin_knife", "cmdSkinSelectKnife");
```

这三个命令让玩家**直接跳转到**对应类型的皮肤选择菜单，不用先打开主菜单再选。

### 2.2.7 注册服务器命令（第 153-155 行）

```pawn
register_srvcmd("skinsys_giveallskins_menu", "srvCmdGiveAllSkins");
register_srvcmd("skinsys_giveskin_menu", "srvCmdGiveSkinMenu");
```

`register_srvcmd` 注册**服务器命令**（server command），只能由服务器端调用，玩家不能直接输入。这两个命令是给菜单内部用的：菜单选项被点击后，通过 `server_cmd` 调用它们。

> 这是一种常见模式：菜单 → `server_cmd` → 服务器命令 → 执行逻辑。为什么绕一圈？因为菜单回调函数拿到的信息有限，通过 server_cmd 可以传更多参数。

### 2.2.8 注册 M 键菜单（第 162 行）

```pawn
register_clcmd("say /skinmenu", "cmdMenu");
```

`cmdMenu` 会执行 `client_cmd(id, "chooseteam")`，即打开 CS 原生的选队菜单。这是"按 M 键"的替代方案。

### 2.2.9 注册菜单（第 164-181 行）

```pawn
register_menucmd(register_menuid("HnsSkinSkinSelect"), 1023, "handleSkinSelectMenu");
register_menucmd(register_menuid("HnsSkinGiveSelectPlayer"), 1023, "handleGiveSelectPlayer");
register_menucmd(register_menuid("HnsSkinGiveSelectType"), 1023, "handleGiveSelectType");
register_menucmd(register_menuid("HnsSkinGiveSelectSkin"), 1023, "handleGiveSelectSkin");
register_menucmd(register_menuid("HnsSkinGiveSelectSkinList"), 1023, "handleGiveSelectSkinList");
```

`register_menuid` 给菜单起一个**名字**，返回菜单 ID。`register_menucmd` 把"这个菜单被点击"和"处理函数"绑定起来。

第二个参数 `1023` 是**按键掩码**。1023 = 二进制 `1111111111`，表示允许按 0-9 十个键。

> 注意：主菜单 `HnsSkinMainMenu` 没有在这里注册 menucmd，而是用 `show_menu` 时传了菜单名。看第 6 课会明白，主菜单用的是另一种注册方式（其实在源码里主菜单的 handler 是 `handleSkinMainMenu`，通过 `show_menu` 的最后一个参数关联）。

### 2.2.10 注册管理员命令（第 168-175 行）

```pawn
register_clcmd("say /giveallskins", "cmdGiveAllSkins");
register_clcmd("say /giveskin", "cmdGiveSkinMenuStart");
register_clcmd("say /giveskinmenu", "cmdGiveSkinMenuStart");
register_clcmd("say /giveskinid", "cmdGiveSkinCmd");
```

| 命令 | 触发函数 | 说明 |
|------|---------|------|
| `/giveallskins` | `cmdGiveAllSkins` | 命令行批量发放 |
| `/giveskin` | `cmdGiveSkinMenuStart` | 菜单发放 |
| `/giveskinmenu` | `cmdGiveSkinMenuStart` | 菜单发放（别名） |
| `/giveskinid` | `cmdGiveSkinCmd` | 命令行单个发放 |

这些命令在函数内部会检查管理员权限（第 8 课详讲）。

### 2.2.11 注册事件钩子（第 184 行）

```pawn
RegisterHookChain(RG_CBasePlayer_Spawn, "OnPlayerSpawn", true);
```

`RegisterHookChain` 是 ReGameDLL 的**钩子系统**。`RG_CBasePlayer_Spawn` 是"玩家出生"事件。第三个参数 `true` 表示 **post 钩子**（事件发生后调用）。

> 也就是说：每当有玩家出生，就会调用 `OnPlayerSpawn`，在里面重新应用皮肤。这样玩家每次复活都会穿上自己选的皮肤。

### 2.2.12 确保目录存在（第 186-192 行）

```pawn
new szDir[256];
get_localinfo("amxx_configsdir", szDir, charsmax(szDir));
format(szDir, charsmax(szDir), "%s/mixsystem", szDir);
if (!dir_exists(szDir)) {
    mkdir(szDir);
}
```

`get_localinfo` 获取 AMXX 的配置目录路径（通常是 `addons/amxmodx/configs`）。然后拼上 `/mixsystem`，检查这个目录是否存在，不存在就创建。

> 这里有一个 `if`：`if (!dir_exists(szDir))`。它的意思是"如果目录不存在"。`!` 是取反，`dir_exists` 返回真（存在）或假（不存在），取反后就是"不存在时进入 if"。这是插件里第一个典型的防御性检查。

### 2.2.13 记录日志（第 194 行）

```pawn
log_amx("[SkinSystem] 插件加载完成");
```

`log_amx` 把信息写入 AMXX 的日志文件，方便排查问题。

## 2.3 plugin_end：清理阶段（第 288-296 行）

```pawn
public plugin_end() {
    if (g_iVault != INVALID_HANDLE) {
        nvault_close(g_iVault);
    }
    cleanup_arrays();
    server_print("[SkinSystem] plugin_end: 清理完成");
}
```

`plugin_end` 在插件卸载时调用，做两件事：
1. `if (g_iVault != INVALID_HANDLE)` —— 如果数据库句柄有效，就关闭它（释放资源）
2. `cleanup_arrays()` —— 销毁所有动态数组（释放内存）

> 这里又是一个 `if`：`if (g_iVault != INVALID_HANDLE)`。为什么要有这个判断？因为如果 `nvault_open` 失败了，`g_iVault` 还是初始值 `INVALID_HANDLE`，直接 `nvault_close` 一个无效句柄可能出错。先判断再操作，是防御性编程。

## 2.4 小结

这一课我们看到了插件的完整生命周期：

```
服务器启动 → plugin_precache（加载模型）→ plugin_init（注册一切）
玩家进出 → client_putinserver / client_disconnected（第 11 课）
插件卸载 → plugin_end（清理）
```
