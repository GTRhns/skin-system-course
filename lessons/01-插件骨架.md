# 第 1 课：插件骨架

> 覆盖源码第 1-110 行。这一课讲清楚：头文件、常量、全局变量，也就是一个插件的"骨架"。

---

## 1.1 文件头注释（第 1-20 行）

```pawn
/*
 * HnsSkin - 独立开源皮肤系统
 * 基于 HNS Match Skin 重构，去除所有 HNS 比赛系统依赖
 *
 * 功能:
 * 1. 普通玩家皮肤系统 (读取 player_models.ini)
 * 2. 统一主菜单 (/skin)
 * 3. 皮肤发放机制 (/give skin, /take skin)
 *
 * 命令:
 * /skin - 打开主菜单 (T/CT/刀皮肤)
 * /skin_t - 直接打开T皮肤选择
 * ...
 */
```

`/* */` 是**块注释**，编译器会忽略里面的内容，纯粹给人看的。这里写的是这个插件的"自我介绍"：它是什么、有什么功能、有哪些命令。

> 注意：这里写的命令列表是**给人看的文档**，不是代码。真正的命令注册在 `plugin_init` 里（第 2 课会讲）。

## 1.2 头文件 include（第 22-27 行）

```pawn
#include <amxmodx>
#include <fakemeta>
#include <amxmisc>
#include <reapi>
#include <nvault>
```

`#include` 是**预处理指令**，作用是把别的文件的内容"复制"进来。这 5 个文件是 AMXX 的**模块头文件**，提供了各种函数：

| 头文件 | 提供什么 |
|--------|---------|
| `amxmodx` | 核心：注册插件、命令、菜单、日志 |
| `fakemeta` | 底层实体操作：`set_pev`、`precache_model` |
| `amxmisc` | 杂项工具：`get_user_authid`、`get_user_ip` |
| `reapi` | ReGameDLL 扩展：`rg_set_user_model`、`RegisterHookChain` |
| `nvault` | 数据持久化：`nvault_set`、`nvault_get` |

> 第 28 行 `// pev_viewmodel is 27...` 是单行注释，提醒作者 `pev_viewmodel` 的编号。

## 1.3 前向声明（第 30-32 行）

```pawn
stock bool:has_skin(const id, const iType, const iSkinIndex);
stock give_skin(const id, const iType, const iSkinIndex);
```

这叫做**前向声明（forward declaration）**。它告诉编译器："后面会定义这两个函数，签名是这样的，先用起来。"这样其他函数在它们定义之前就能调用它们。

> 为什么需要？因为 Pawn 编译器是"从上往下"读的，如果函数 A 调用了还没定义的函数 B，就会报错。前向声明就是提前打个招呼。

## 1.4 插件信息（第 36-39 行）

```pawn
#define PLUGIN_NAME "HnsSkin Skin System"
#define PLUGIN_VERSION "1.0.0"
#define PLUGIN_AUTHOR "OpenSkin"
```

`#define` 是**宏定义**，就是"文本替换"。以后代码里写 `PLUGIN_NAME`，编译器会把它替换成 `"HnsSkin Skin System"`。

这三个宏会在 `plugin_init` 里传给 `register_plugin`，用来在服务器上显示插件名、版本、作者。

## 1.5 常量定义（第 43-51 行）

```pawn
#define MAX_AUTHID_LENGTH    64
#define MAX_MODEL_NAME      128
#define MAX_SKIN_NAME       64
#define MAX_PLAYERS_DATA    512
#define MAX_OWNED_SKINS     64
#define MAX_MENU_PAGE       7
#define Invalid_Array       -1
#define EOS                 0
```

这些是**魔法数字的命名**。解释几个关键的：

| 常量 | 值 | 含义 |
|------|-----|------|
| `MAX_AUTHID_LENGTH` | 64 | SteamID / IP 字符串的最大长度 |
| `MAX_MODEL_NAME` | 128 | 模型路径字符串的最大长度 |
| `MAX_OWNED_SKINS` | 64 | 一个玩家最多拥有多少皮肤 |
| `MAX_MENU_PAGE` | 7 | 菜单每页显示几项 |
| `Invalid_Array` | -1 | 无效数组句柄的标志 |
| `EOS` | 0 | End Of String，字符串结尾的空字符 `'\0'` |

> `EOS` 特别重要。在 Pawn 里，字符串用 `\0`（值为 0）结尾。判断"字符串是不是空的"就是判断 `szName[0] == EOS`。

## 1.6 权限等级（第 53-57 行）

```pawn
#define PERM_NONE           0
#define PERM_VIP            1
#define PERM_ADMIN          2
#define PERM_OWNER          3
```

这是这个插件自己定义的**权限分级**：0=无权限，1=VIP，2=管理员，3=服主。后面 `get_user_perm_level` 会返回这些值。

## 1.7 菜单 ID（第 59-66 行）

```pawn
#define MENU_PLAYER_MAIN    8001
#define MENU_JOIN_TEAM      8002
#define MENU_SKIN_MAIN       8003
#define MENU_SKIN_SELECT     8004
#define MENU_GIVE_PLAYER     8007
#define MENU_GIVE_TYPE       8008
#define MENU_GIVE_SKIN       8009
```

这些是**菜单编号**。注意：**这些常量在本版本里其实没有被直接使用**（菜单是用 `register_menuid("名字")` 注册的），它们是早期设计留下的"规划"，方便以后用数字引用菜单。这算是一个小历史遗留，不影响功能。

## 1.8 全局变量：模型数组（第 70-76 行）

```pawn
new Array:g_aTModels;          // T模型路径
new Array:g_aTModelNames;     // T模型显示名称
new Array:g_aCTModels;         // CT模型路径
new Array:g_aCTModelNames;    // CT模型显示名称
new Array:g_aKnifeModels;      // 刀模型路径
new Array:g_aKnifeModelNames; // 刀模型显示名称
```

`Array:` 是 AMXX 的**动态数组类型**。它像一个可以无限增长的列表，用 `ArrayCreate` 创建，用 `ArrayPushString` 往里面加字符串，用 `ArrayGetString` 取出来。

这里定义了 6 个数组，两两一组（路径 + 名称），对应三种皮肤：T 土匪、CT 警察、刀。

> 为什么路径和名称分开存？因为菜单里要显示"北极战士"这样的中文名，但实际加载模型要用 `models/player/arctic/arctic.mdl` 这样的路径。一个管显示，一个管加载。

## 1.9 全局变量：玩家拥有的皮肤（第 78-84 行）

```pawn
new g_iOwnedT[MAX_PLAYERS + 1][MAX_OWNED_SKINS];
new g_iOwnedTCount[MAX_PLAYERS + 1];
new g_iOwnedCT[MAX_PLAYERS + 1][MAX_OWNED_SKINS];
new g_iOwnedCTCount[MAX_PLAYERS + 1];
new g_iOwnedKnife[MAX_PLAYERS + 1][MAX_OWNED_SKINS];
new g_iOwnedKnifeCount[MAX_PLAYERS + 1];
```

`MAX_PLAYERS` 是 AMXX 内置常量，通常是 32。所以 `g_iOwnedT[MAX_PLAYERS + 1]` 就是 `g_iOwnedT[33]`——**每个玩家一个槽位**。

- `g_iOwnedT[id]` 是一个数组，存玩家 id 拥有的所有 T 皮肤索引
- `g_iOwnedTCount[id]` 是一个数字，记录他拥有多少个

> 为什么用 `MAX_PLAYERS + 1` 而不是 `MAX_PLAYERS`？因为玩家 id 从 1 开始（0 是无效 id），所以数组要留 33 个位置（0-32）。

## 1.10 全局变量：当前选择的皮肤（第 86-89 行）

```pawn
new g_iSelectedT[MAX_PLAYERS + 1] = {-1, ...};
new g_iSelectedCT[MAX_PLAYERS + 1] = {-1, ...};
new g_iSelectedKnife[MAX_PLAYERS + 1] = {-1, ...};
```

这三个数组记录每个玩家**当前选中的**皮肤索引。`{-1, ...}` 表示"所有元素初始化为 -1"。

> 为什么初始是 -1？因为 -1 表示"还没选任何皮肤"。皮肤索引从 0 开始，所以 -1 是一个安全的"空"值。后面代码里到处检查 `if (g_iSelectedT[id] >= 0)`，就是在问"他选了吗？"

## 1.11 全局变量：菜单临时状态（第 91-93 行）

```pawn
new g_iSkinSelectType[MAX_PLAYERS + 1];   // 0=T, 1=CT, 2=Knife
new g_iSkinSelectPage[MAX_PLAYERS + 1];
```

这两个数组记录玩家**正在浏览的菜单状态**：
- `g_iSkinSelectType[id]`：他正在看哪个类型的皮肤（T/CT/刀）
- `g_iSkinSelectPage[id]`：他翻到第几页了

> 为什么要存这些？因为玩家打开菜单后，可能切出去聊天，再回来时菜单还要记得他翻到哪了。这些"跨函数共享的临时状态"就存在全局变量里。

## 1.12 全局变量：发放状态（第 97-100 行）

```pawn
new g_iGiveTarget[MAX_PLAYERS + 1];       // 发放目标玩家
new g_iGiveType[MAX_PLAYERS + 1];        // 发放类型 0=T, 1=CT, 2=Knife
new g_iGivePage[MAX_PLAYERS + 1];        // 发放菜单翻页
```

管理员发放皮肤时，要经过"选玩家 → 选类型 → 选皮肤"好几步。这几步之间要记住中间状态，就存在这三个数组里。

## 1.13 全局变量：玩家标识（第 104-107 行）

```pawn
new g_szPlayerAuth[MAX_PLAYERS + 1][MAX_AUTHID_LENGTH];
new g_szPlayerIP[MAX_PLAYERS + 1][MAX_AUTHID_LENGTH];
new g_szPlayerName[MAX_PLAYERS + 1][32];
```

每个玩家的 SteamID、IP、名字，各存一份。用于存档的标识和显示。

## 1.14 nvault 句柄（第 109-110 行）

```pawn
new g_iVault = INVALID_HANDLE;
```

`g_iVault` 是 nvault 数据库的**句柄**（相当于一把钥匙）。`INVALID_HANDLE` 表示"还没打开"。第 2 课会看到它在 `plugin_init` 里被 `nvault_open` 打开。

## 1.15 小结

这一课我们认识了插件的骨架：
- 头文件提供函数库
- 常量定义"魔法数字"的名字
- 全局变量记录所有状态（模型、玩家皮肤、菜单、发放）

> 记住一个核心思想：**全局变量就是插件的"记忆"**。插件不运行的时候没有记忆，运行的时候全靠这些变量记住一切。
